# 記事構造テンプレート（Writing Agent 文体・フォーマット基準）

> **役割**: このファイルは Writing Agent が参照する「完成記事の構造・文体・フォーマット基準」です。
> 実際の記事を書く際は、本テンプレートの章構成・文体スタイル・表フォーマットを踏襲してください。
> `{{変数名}}` は記事仕様JSON（Parser Agent の出力）から埋め込まれます。

---

## 変数定義（記事仕様JSONとの対応）

| 変数名 | 取得元 | 説明 |
|--------|--------|------|
| `{{SERIES_NAME}}` | 記事仕様JSON > series_name | シリーズ名 |
| `{{EPISODE_NUMBER}}` | 記事仕様JSON > episode | 回数 |
| `{{TITLE}}` | 記事仕様JSON > title | 記事タイトル |
| `{{CONCLUSION}}` | 記事仕様JSON > conclusion | 記事の結論（一文） |
| `{{TARGET_READERS}}` | 記事仕様JSON > target_readers | 対象読者リスト |
| `{{SECTION_1}}` 〜 `{{SECTION_N}}` | 記事仕様JSON > sections | 各章の見出し |
| `{{NEXT_EPISODE_BRIDGE}}` | 記事仕様JSON > next_episode_bridge | 次回への接続文 |
| `{{TOPIC_DOMAIN}}` | prompt/記事作成プロンプト.md | テーマドメイン |
| `{{CTA_GOOD_EXAMPLE}}` | prompt/記事作成プロンプト.md | 良いCTA例 |

## 記事構造（9章必須）

---

### 連載表記（記事冒頭）

```
連載：{{SERIES_NAME}}｜第{{EPISODE_NUMBER}}回
```

---

### 第1章：タイトル

**フォーマット**:
```
{{TITLE}}
```

**文体ガイド**:
- 読者が抱える問題・リスク・判断を示す言葉を含める
- 「〜とは」「〜の方法」などの一般論タイトルを避ける
- 30〜50文字を目安とする

---

### 第2章：リード文

**フォーマット**:
```
（読者の現実的な違和感・痛みを突く1〜2文）

（よくある状況と、しかし何かが足りないという対比）

（記事の問いを明確にする1文）

（記事で論じることの予告：「本稿では、〜を〜に分けて考える」）

（記事の核心メッセージの伏線：「この問いに答えられる企業はどれだけあるだろうか」）
```

**サンプル構造（AI経営実装 第1回より）**:
```
AIの利用率は上がっている。研修受講者も増えている。PoCも実施した。
それでも、取締役会で「売上・粗利・リードタイムにどう効いたのか」と問われたとき、
明確に答えられる企業はどれだけあるだろうか。

よくある報告         ｜ 本当に知りたいこと
月間ログイン率が上昇  ｜ どの業務の処理時間が何％短縮したか
...（比較表形式）

本稿では、〜を4つに分けて考える。
```

---

### 第3章：課題の経営・事業化

**フォーマット**:
```
（節タイトル）

（統計・調査データを使った現状の定量的な描写）
▼ （可視化が必要な場合は表・図を挿入）
（データが示す本質的な意味の解説）

（なぜこれが現場課題ではなく経営課題なのかの説明）
（投資・ROI・機会損失・ガバナンス・説明責任への接続）
```

**文体ガイド**:
- 出典名・調査名・発表年を本文中に明記する（括弧書き）
- 数字は具体的に（「〜%」「〜万件」）
- データの後に必ず「しかし」または「だが」で問題を掘り下げる

---

### 第4章：構造的原因の分解

**フォーマット**:
```
（節タイトル）

（よくある失敗パターンの提示）
（最も深刻なパターンの指摘：「最も深刻なのは〜」）

▼ （具体的な業務フロー比較表）
（表の解説：何が変わって何が変わっていないかの分析）

（構造的原因の明示：業務プロセス・KPI・責任範囲・ガバナンスの問題として整理）
```

**表フォーマット例**:
```
| プロセス工程 | 導入前 | 導入後 |
|------------|--------|--------|
| （工程名）  | （状態）| （状態）|
| ...        | ...    | ...    |
| 合計リードタイム | 約X日 | 約Y日（≒変化なし） |
```

---

### 第5章：独自フレームワーク

**フォーマット**:
```
（節タイトル）

（このフレームワークが必要な理由の1〜2文）
（フレームワークの全体像の説明）

▼ （フレームワーク本体：表またはチェックリスト形式）

（フレームワークの見方・使い方の解説）
（各要素が欠けるとどうなるかの示唆）
```

**フレームワーク表フォーマット例**:
```
| 設計要素 | 実施すること | 欠けると起きること |
|---------|------------|-----------------|
| ①要素名 | （判断・設計内容） | （失敗パターン） |
| ②要素名 | ...         | ...             |
...
```

**チェックリストフォーマット例**:
```
□ （確認項目1）
□ （確認項目2）
□ （確認項目3）
...
```

---

### 第6章：実務例

**フォーマット**:
```
（節タイトル）

（企業・業務の具体的な状況設定）
（AI/変化導入前後の具体的な変化の描写）

注目すべきは〜（単なる数字ではなく設計・判断の話へ）
（成果が出た理由の構造的な解説）

さらに〜（より発展した取り組みへの言及）

（出典・参照先）
```

**文体ガイド**:
- 架空の事例の場合は「ある〇〇業の〇〇チームが」と匿名化して表現
- 実企業の場合は「（企業名公式発表・年月）」と出典を必ず記す
- 事例の後に「注目すべきは数字ではなく、そこに至る設計だ」のような構造解説を必ず入れる

---

### 第7章：読者が取るべきアクション

**フォーマット**:
```
（節タイトル）

（アクション全体の概観1文）

① （問い・アクション1のタイトル） ｜ （説明文）
② （問い・アクション2のタイトル） ｜ （説明文）
...

または

▼ （比較表：よくある順番 vs あるべき順番）

（まとめの一言：差は〜の差ではなく〜の差である）

▼ （観点別の比較表）
| 観点 | 従来型 | 理想型 |
|------|--------|--------|
| ...  | ...    | ...    |
```

---

### 第8章：まとめ

**フォーマット**:
```
おわりに：（読者の状況を象徴するキャッチコピー）

（冒頭の問いへの回帰：「問われているのは〜ではなく、〜か、である」）
（記事の結論を「〜の問題」として再定義）

（外部環境・社会的文脈でのインパクト：調査データや社会変化による根拠）
（放置した場合に失うものの明示）

次回は、〜を扱う。
（次回の問題意識と論点の予告）
第〇回では、〜を具体的に論じる。
```

---

### 第9章：CTA（受注・行動導線）

**フォーマット**:
```
【ご相談について】

「（読者の課題・状況を再提示した一文）」と感じている方は、
まず（最初に取るべき行動）から始めるべきです。
私たちの初回診断では、（診断のフレーム名）に基づき以下の論点を整理します。

【初回診断で整理する〇つの論点】

（論点ラベル）：（具体的な診断内容の説明）
（論点ラベル）：（具体的な診断内容の説明）
...

（締めの一文：何のために相談するのかを自然に示す）
```

**文体ガイド**:
- 「お気軽にご相談ください」で終わらせない
- 「初回診断で整理するN個の論点」のように、得られる成果物を具体的に示す
- 診断後に何が分かるのかを列挙する（現状把握・課題特定・優先順位・90日アクションなど）

## 文体・表現の一般基準

### 使って良い表現
- 「〜の構造を解剖する」「〜を提示する」「〜に踏み込む」
- 「〜が示す数字は厳しい」「〜という事実だ」
- 「注目すべきは数字ではなく、そこに至る設計だ」
- 「問われているのは〜ではなく〜か、である」

### 避けるべき表現
| 避ける表現 | 代替表現 |
|---------|---------|
| 圧倒的多数 | 多くの企業（出典付き） |
| 必ず〜できる | 〜と考えられる |
| 劇的に改善 | 前年比〇〇倍（出典付き） |
| お気軽にご相談 | 初回診断では〜を整理します |
| 通用しない | 〜では十分ではない |
| 本当の理由 | 構造的な原因 |

### 出典記載フォーマット
```
（出典名「調査名」年月）
例：（BCG「From Potential to Profit」2025年1月）
例：（NRI「ユーザー企業のIT活用実態調査2025」）
```
